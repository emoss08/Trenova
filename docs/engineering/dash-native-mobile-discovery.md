# Dash → native iOS (Swift) and Android (Kotlin): discovery

Status: discovery / not yet approved
Scope: replacing `client/apps/dash` (the driver portal) with first-party native apps

## Summary

The UI is the cheap part. Dash is ~6.4k lines of non-test source across 11 routes and 21
components — rebuilding that twice in SwiftUI and Compose is real work, but it is bounded,
well-understood work.

The expensive part is that Dash is not just a React app; it is a *browser* client. Four of
the platform contracts it rides on are browser-shaped and have no native path today:

| Contract | Today | Native status |
|---|---|---|
| Authentication | `HttpOnly` session cookie + CSRF token + browser-provenance guard | **Blocked** — no token grant for a non-browser user agent |
| GraphQL transport | Persisted-operation safelist, hashes generated by the TypeScript codegen | **Blocked** — prod/staging reject any hash not in the Go-embedded manifest |
| Realtime | `@foony/realtime` over a vendor-internal binary WebSocket framing | **Blocked** — JS and Go SDKs only; the framing is explicitly not an integration surface |
| Push | Web Push / VAPID, subscriptions stored as `endpoint`/`p256dh`/`auth` | **Blocked** — no APNs or FCM path, no device-token model |

None of those are hard problems individually. All four are backend problems, all four are
shared between iOS and Android, and all four must land before *either* app can ship a login
screen that works. That ordering is the single most important finding here: **sequence the
platform work first and treat the two native clients as the second phase**, or you will have
two mobile teams blocked on the same four tickets.

Rough shape: ~10–14 engineer-weeks of backend/platform work, then ~20–28 engineer-weeks per
platform. Those are ranges with wide error bars, not commitments; the assumptions behind them
are in [Sizing](#sizing).

## Why native is the right call here

The stated reasons (performance, device compatibility) are true but undersell it. Reading what
Dash actually does, the case for native is mostly about capabilities it cannot reach at all
today:

- **Offline.** `client/apps/dash/public/dash-sw.js` is a push-and-click handler and nothing
  else — there is no cache, no precache, no offline route. A driver in a dead zone currently
  sees a blank app. For a load/HOS/document app used from the cab, this is the biggest gap.
- **Arrival detection.** `RecordMyStopAction`
  (`services/tms/internal/core/services/driverportalservice/portal.go:349`) is driver-initiated
  today. Background location + geofencing turns arrive/depart into something the phone observes
  rather than something the driver remembers to tap. The geofence domain already exists
  (`internal/core/domain/geofence/`).
- **Document capture.** Uploads go through plain multipart form posts
  (`internal/api/handlers/driverportalhandler/handler.go:47-56`). Native gets edge detection,
  perspective correction, multi-page capture, and retry-from-disk for BOLs, receipts, and
  credential documents.
- **Reliable notifications.** Web Push on iOS requires the PWA to be added to the home screen
  and is unreliable in practice. Driver assignment offers (`RespondToMyAssignment`) are
  time-sensitive; this matters.
- **Biometric unlock, and fleet distribution via MDM / Apple Business Manager.**

Performance is a real but secondary win. The React Native/Expo question is settled per the
request; nothing below revisits it.

## What Dash is today

**Routes** (`client/apps/dash/src/router.tsx`) — 11:
`/dash/login`, `/dash/accept`, `/dash` (home), `/dash/loads`, `/dash/loads/:assignmentId`,
`/dash/pay`, `/dash/pay/:settlementId`, `/dash/money`, `/dash/hos`, `/dash/notifications`,
`/dash/profile`.

**Source**: 6,432 non-test LOC + 1,158 test LOC. 21 components, 3 hooks, 2 pure-logic modules
(`src/lib/settlement.ts` at 77 lines, `src/lib/hos.ts` at 46 lines).

**Data surface**: 37 `My*` GraphQL operations in the persisted manifest (of 716 total), plus 8
REST endpoints under `/portal/` for document types, uploads, and invitation accept/preview.

**Feature gating**: `MyPortalFeatures` returns ~19 toggles (`useDashFeatures`,
`internal/core/services/driverportalservice/features.go`) that decide which UI renders. The
server enforces every one of them independently, which is exactly the property a native client
needs — the app can render optimistically without becoming a security boundary.

**i18n**: 4 locales (`en`, `es`, `zh-TW`, `zh-CN`) from `i18n/messages.*.json`, 19,448 source
messages, 433 `t()` call sites inside Dash.

**HOS is read-only.** `MyHosState` / `MyHosDailyLogs` / `MyHosViolations` display data sourced
from the telematics provider (`internal/core/domain/telematics/`). The app is an HOS *viewer*,
not an ELD. Keep it that way — see [Risks](#risks-and-open-questions).

## The four blockers, in detail

### 1. Authentication has no non-browser path

`services/tms/internal/api/middleware/auth.go:55` accepts exactly two credentials:

- A session cookie (`authenticateWithSession`, line 63) → sets a full user auth context.
- A `Bearer` API key (`authenticateWithBearer`, line 110) → sets an **API-key principal**, not a
  user. There is a test asserting exactly this:
  `TestRequireAuth_ValidBearerAPIKeyDoesNotSetUserContext` (`auth_test.go:173`).

Every `My*` resolver reads `authCtx.UserID`, so API keys cannot drive the portal. That leaves
cookies, and cookies drag three more things along:

- `CSRFMiddleware.RequireToken` (`middleware/csrf.go:53`) requires a header token derived from
  the session id for every unsafe method by a user principal. Bootstrapped over `GET /auth/csrf`.
- `CSRFBrowserGuard.violation` (`middleware/csrf.go:108`) inspects `Sec-Fetch-Site`, `Origin`,
  and `Referer`. A native client sends none of them. With a session cookie present and no
  `Origin`, the guard falls to the `Referer` branch and returns `"missing or untrusted referer"`.
  In `report` mode that is a log line; **in `block` mode every native mutation fails.**
- No refresh semantics. Session lifetime is server-side; there is no renewal a background app
  can perform.

A cookie jar (`HTTPCookieStorage` / OkHttp `CookieJar`) technically works, but you would be
shipping a mobile app that impersonates a browser and then special-casing the guard that exists
to detect exactly that. Don't.

**Recommendation:** add a first-class mobile grant — `POST /auth/mobile/token` returning a
short-lived access token plus a rotating refresh token bound to a device id, with revocation
surfaced in the existing session UI. Access tokens are non-ambient credentials, so the whole
CSRF apparatus is skipped for them (`RequireToken` already short-circuits non-user principals;
it needs a third case for "user principal authenticated by mobile token"). This is the single
largest and most security-sensitive backend item.

### 2. GraphQL only accepts safelisted operation hashes

`internal/api/graphql/persisted_operations.go:331` — when
`enforcePersistedOperations` is true (production and staging, line 330), a request without a
hash, or with a hash absent from the manifest, is rejected. The manifest is `go:embed`-ed at
line 23. It is produced by the TypeScript codegen
(`client/packages/graphql/codegen.ts`, `persistedDocuments: { mode: "replaceDocumentWithHash" }`)
and copied into the Go tree by `scripts/sync-graphql-persisted-documents.mjs`.

So a native app cannot send GraphQL at all unless its operation hashes are in that file.

The naive fix — force Apollo iOS/Kotlin to reproduce graphql-codegen's exact hash — is fragile.
Both Apollo toolchains hash their own normalized document text, and matching a third tool's
normalization byte-for-byte is a standing maintenance tax.

**Recommendation: merge manifests instead of matching hashes.** The server side is just
`hash → query text`, so two different hashes mapping to the same document is completely fine.
Turn `sync-graphql-persisted-documents.mjs` (currently a 13-line `copyFile`) into a merge over
three inputs:

1. `client/packages/graphql/src/generated/persisted-documents.json` (web),
2. Apollo iOS's operation manifest (`operationManifest` in `ApolloCodegenConfiguration`),
3. Apollo Kotlin's `persistedQueryManifest.json` (`operationManifestFormat = "persistedQueryManifest"`).

Then extend `assert-codegen-clean.mjs` to cover the merged output, and add the two mobile
codegen runs to the `Codegen Checks` CI job. Both Apollo toolchains emit base16 SHA-256 in the
standard `extensions.persistedQuery.sha256Hash` shape the server already parses
(`persistedGraphQLPersistedQuery`, line 65), and `normalizePersistedHash` (line 345) already
handles the bare-64-hex form.

Keep all three toolchains pointed at the *same* `client/packages/graphql/src/operations/**/*.graphql`
files and the same `services/tms/internal/api/graphql/schema/*.graphqls`. One schema, one set of
operation documents, three code generators. That is the contract-sharing strategy for this
project — see [Shared code](#shared-code-what-to-share-and-what-not-to).

Note that Apollo Kotlin also exposes `operationIdGenerator`, so hash parity *is* reachable on
Android if you ever want it. iOS has no equivalent documented hook. Merging works for both, so
prefer it.

### 3. Realtime has no native SDK and no documented wire protocol

`client/packages/shared/src/services/realtime.ts` wraps `@foony/realtime`; the server publishes
through `github.com/Foony-Limited/realtime-go`
(`internal/infrastructure/foony/client.go`). Clients mint a token from
`GET /realtime/token-request/` (`internal/api/handlers/realtimehandler/handler.go:33`) and
subscribe to `tenant:{orgId}:{buId}:data-events`, then map resource names to query-cache
invalidations (`use-dash-realtime.ts`).

Foony publishes **JavaScript and Go SDKs only**. Their protocol documentation states the socket
speaks a compact binary framing that is internal and changes between SDK versions without
notice, and is explicitly not a supported integration surface. A hand-rolled Swift or Kotlin
client is therefore not an option — not "hard", *unsupported*.

Three ways out, in order of preference:

1. **Server-side bridge.** Add an authenticated SSE (or plain WebSocket) endpoint on TMS —
   `GET /portal/events` — where the TMS process, already a Foony subscriber via the Go SDK,
   re-emits the same invalidation envelopes scoped to the caller's tenant and user. One
   implementation, both platforms, no vendor coupling in the apps, and it reuses the mobile
   token from blocker #1. This is also the cheapest thing to make correct: the payload shape is
   already defined by `parseInvalidationEvent` / `RESOURCE_EVENT_NAME`.
2. **Ask Foony for native SDKs.** Worth a conversation, but it puts a roadmap dependency on a
   `0.16.0` vendor.
3. **Push + pull-to-refresh only.** Viable for a v1 if the bridge slips; a driver app tolerates
   30-second staleness far better than a dispatch board does. Not viable for `load-chat`.

### 4. Push is Web Push only

`internal/api/handlers/pushhandler/handler.go:40-43` exposes VAPID public key + subscribe +
unsubscribe. The stored subscription is Web Push-shaped —
`Endpoint`/`P256dh`/`Auth`, validated as a URL
(`internal/core/domain/notification/pushsubscription.go:23`) — and delivery goes through
`webpushservice`. Config carries only `vapidPublicKey`/`vapidPrivateKey`
(`config.go:1561`).

Native needs a device-token model (`platform`, `token`, `appVersion`, `deviceId`, `locale`),
APNs (token-based auth, p8 key) and FCM v1 dispatchers behind the existing notification service,
plus collapse keys and a deep-link payload contract shared with the Web Push payload that
`dash-sw.js` already consumes. Keep Web Push working — the PWA should not be deleted on day one.

## Also needed, but not blocking

- **Portal API gaps for mobile.** `useLoad(assignmentId)` currently fetches *both* `Active` and
  `History` scopes at 25 each and filters client-side (`src/_components/use-loads.ts`). That is
  bad on LTE and worse on battery. Add `MyLoad(assignmentId:)`, cursor pagination for
  `MySettlements`, and one aggregated home query to collapse the home screen's round trips.
- **A delta/sync endpoint** if offline is in scope — a `since`-cursor over the resources Dash
  caches, so a cold start after a dead zone is one call rather than fifteen.
- **Deep links.** The invitation flow is a token in a query string
  (`/dash/accept?token=…`, `src/routes/accept.tsx`). Native needs Universal Links + App Links
  association files served from the portal domain (`PortalConfig.BaseURL`, `config.go:1549`),
  plus a fallback to the web page when the app is not installed.
- **Minimum-version gate.** A mobile client the server can reject by version is the only way to
  retire an operation from the safelist safely; web ships atomically, phones do not.
- **i18n pipeline.** `i18n/tools/` extracts from TS. It needs a target that emits
  `.xcstrings` / `Localizable.strings` and Android `strings.xml` from the same
  `messages.*.json`, or the four locales will drift immediately.
- **Design tokens.** Dash uses 18 of the 70 shared UI components. Do not port the component
  library — port the *tokens* (color, spacing, type scale, the `RingGauge` and
  `SegmentedControl` semantics) and rebuild in SwiftUI/Compose idioms.

## Architecture

### Recommended: native UI on both platforms, shared contract only

- **iOS**: Swift 6 / SwiftUI, `@Observable` state, SwiftData or GRDB for the offline store,
  Apollo iOS for GraphQL, Keychain for the refresh token, `URLSession` background uploads.
- **Android**: Kotlin / Jetpack Compose, ViewModel + Flow, Room for the offline store, Apollo
  Kotlin, EncryptedSharedPreferences or the Keystore for the refresh token, WorkManager for
  uploads and retry.
- **Shared**: the GraphQL schema and operation documents, the merged persisted manifest, the
  i18n catalogs, the design tokens, and a golden-fixture test suite (below).

### Kotlin Multiplatform: considered, not recommended for v1

KMP with native UI would still satisfy the "native app" requirement, and the shared layer would
be the networking + models + business math. But the business math here is
`settlement.ts` + `hos.ts` = **123 lines**. Sharing 123 lines of pure arithmetic does not pay
for a KMP toolchain spanning two platform teams, an extra build system on CI, and Apollo
Kotlin's multiplatform configuration. Duplicate those two modules and pin them together with a
shared JSON fixture file that both platforms run their unit tests against — same protection,
a fraction of the cost.

Revisit KMP if the offline sync engine grows large. That is where the duplication would actually
start to hurt.

### Repository layout

Native code does not belong in `client/` — that is a pnpm/Turborepo workspace and Xcode/Gradle
will fight it. Proposed:

```
mobile/
├── ios/          # Xcode project, SwiftPM deps
├── android/      # Gradle project
└── shared/       # design tokens, golden fixtures, generated i18n, codegen configs
```

`go.work` is untouched. `client/packages/graphql` stays the single source of GraphQL truth and
grows two additional codegen outputs.

## Sizing

Rough, assuming one senior engineer per platform plus backend help. Wide error bars.

**Platform / backend (must land first, shared by both apps): ~10–14 weeks**

| Work | Estimate |
|---|---|
| Mobile token grant + refresh rotation + revocation + CSRF exemption path | 3–5 wk |
| APNs + FCM dispatch, device-token model, payload contract | 2–3 wk |
| Realtime SSE bridge (`/portal/events`) | 2–3 wk |
| Portal API gaps (`MyLoad`, pagination, aggregated home, delta sync) | 2–3 wk |
| Persisted-manifest merge + CI codegen checks | 3–5 d |
| Deep links, min-version gate, i18n export targets | 1–2 wk |

**Per platform: ~20–28 weeks**

| Work | Estimate |
|---|---|
| Foundations: networking, auth, secure storage, DI, codegen wiring, tokens, theming, i18n | 4–6 wk |
| 11 screens + the component equivalents | 8–12 wk |
| Offline cache + mutation queue + conflict handling | 3–4 wk |
| Camera capture, uploads, biometrics, push handling, deep links | 2–3 wk |
| Accessibility, QA, store submission, MDM packaging | 2–3 wk |

The two platforms parallelize after foundations. They do not parallelize with the backend phase.

## Phasing

1. **Phase 0 — spike (2–3 wk).** One throwaway iOS app that logs in against a prototype token
   grant, runs `MyLoads` through Apollo iOS with a merged-manifest hash, and receives one APNs
   notification. This de-risks all four blockers before anyone commits to a roadmap. If the
   manifest merge does not work end to end, you want to know in week 2, not month 4.
2. **Phase 1 — platform.** The backend table above. Ship it behind the existing web app; the
   PWA keeps working throughout.
3. **Phase 2 — iOS and Android foundations + read-only screens.** Loads, load detail, HOS, pay,
   settlement, profile. Internal TestFlight / internal track.
4. **Phase 3 — write paths.** Assignment response, stop actions, expenses, PTO, disputes,
   document upload, chat. This is where the offline mutation queue earns its keep.
5. **Phase 4 — native-only capabilities.** Background geofenced arrival detection, document edge
   detection, biometric unlock.
6. **Phase 5 — PWA disposition.** Keep Dash as the fallback for unsupported devices and desktop;
   do not delete it. Decide then whether it goes into maintenance.

## Risks and open questions

**Needs a product decision before Phase 1:**

- **One app or one app per carrier?** Trenova is multi-tenant. A single "Trenova Dash" in both
  stores is far cheaper to operate; per-carrier white-labeled builds mean a build-and-submit
  pipeline per tenant, 50+ store listings, and a review queue you do not control. If carriers
  will demand their own branding, that changes the architecture and should be decided now.
- **Which of the 11 routes are v1?** Loads + HOS + pay are the driver's daily surface.
  Reviews, training, disciplinary actions, and shift swaps are arguably fine staying on web.
- **Offline scope.** Read-only cache is cheap; a full offline mutation queue with conflict
  resolution is the difference between Phase 3 being 3 weeks and 8.

**Technical risks:**

- **HOS and FMCSA.** The app displays ELD-sourced HOS. It is not a recording device and must not
  become one casually — if duty-status *recording* is ever added, FMCSA §395.20 and Appendix A
  registration and certification apply, which is a different project with a compliance budget.
  Worth writing down now so nobody adds a "change duty status" button in a sprint.
- **Foony.** No native SDK, undocumented framing, `0.16.0`. The SSE bridge removes the apps'
  exposure but not the backend's.
- **App Store review.** A multi-tenant driver portal needs a working demo account for Apple
  review (Guideline 2.1) and will be read against Guideline 4.2 minimum-functionality. Plan for
  a review rejection cycle on first submission.
- **Safelist and rollout.** Once phones are in the field, an operation can only be retired from
  `persisted-documents.json` after the min-version gate has drained the clients that use it. Add
  that to the checklist in `docs/engineering/generated-artifacts.md`.
- **Session semantics.** Refresh-token rotation needs to interact correctly with
  `MustChangePassword`, `RequiresRoleActivation`, and portal-user session flags
  (`internal/core/services/authservice/service.go:679`). Portal drivers authenticate by password
  today; MFA only arrives through OIDC claims (`service.go:895`), so if MFA is ever required for
  drivers, the mobile grant must carry a challenge step.
